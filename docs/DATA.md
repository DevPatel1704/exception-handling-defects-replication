# Data: sources, revisions, collection and cleaning

**No LLM is used anywhere in the data or analysis pipeline**: no LLM collects, labels, filters, transforms, models
or evaluates data, and no prompts exist. (An LLM coding assistant was used to write parts of the code and docs;
see CONTRIBUTIONS.md. Every number in `results/` comes from executing that code.)

## 2. Collection procedure (new contexts)

Run per target (all inside the `ehrepl` env via `./envrun.sh`):

```bash
python src/collect/clone_repo.py        hibernate-5.1   # clone + worktree at release tag, provenance.json
python src/collect/process_metrics.py   hibernate-5.1   # pre-release process metrics (+ Jira for PRE bugs)
python src/collect/defect_mining.py     hibernate-5.1   # post-release defect labels + manual-validation sample
python src/collect/traditional_metrics.py hibernate-5.1 # product metrics (Understand if licensed, else fallback)
python src/collect/run_analyzers.py     hibernate-5.1   # JTratch (Java 8) on the release worktree
python src/collect/build_dataset.py     hibernate-5.1   # -> data/new/hibernate-5.1/input/File_Level-*.csv
```

| Step | Definition used | Matches paper? |
|---|---|---|
| File universe | `git ls-files` at the release commit, matching `/src/main/java/.*\.java$`, excluding test/testing/documentation/release paths | Yes: the released data contains only `src/main/java` files, no tests. 3,475 files for 5.1.0 vs. 3,488 in the paper's 5.0.0.Final |
| Pre-release window | Non-merge commits in `prev_release_tag..release_tag` (reachable from the release, not from the previous release), rename-aware (paths mapped to their name at the release) | Approximation: the paper used "specific pre-release branches, the date range based on the release notes and the oldest change associated with the release" |
| `Distinct count of Commit Hash PRE` / `Author Email PRE` / `Churn PRE` | distinct commits / distinct lower-cased author e-mails / added+deleted lines (`git log --numstat -M`) | Yes (definitions per §3.3.3) |
| `Distinct count of Issue Key PRE` | distinct Jira keys (`HHH-n`) in pre-window commit messages whose issue is type **Bug** with resolution **Fixed/Done** | Yes (same approach as post-release) |
| Post-release defects (outcome) | distinct Jira keys in commit messages of `release_tag..post_release_tag` (non-merge, rename-aware) whose issue is a Fixed/Done **Bug** **created after** the release commit date; each such commit's modified release files get the issue | Yes, §3.3.1: "fixed defects … ID of the defects to identify code changes … compare the defect report time and the release date". Not SZZ: the bug-*introducing* step is unnecessary for a file-level post-release label |
| Product metrics | SciTools Understand (39 metrics) if `und` + license exist; else **fallback** (`lizard` 1.24.2 + line scanner) with 12 Understand-named approximations | **No for new contexts**: no Understand license, so fallback (see §4) |
| EH metrics | JTratch built from source at tag `eh-model-defects2018`, run on Java 8, then aggregated to file level by `aggregate_jtratch.py`, a re-implementation of the authors' rule sheet | Partially; validated in §3 |
| Merge + missing data | `build_dataset.py` writes the five CSVs in the authors' exact column order; the authors' `0-DataSourcesAnalysis.Rmd` then merges them and drops rows with missing values (MC1), unchanged | Yes (authors' code) |


**Issue trackers.** *Jira* (as in the paper): Bug type, Fixed/Done resolution, keys `ABC-123` in commit
messages. *GitHub Issues* (optional extension, **not** the paper's definition; not used for the results reported here): a bug is a closed issue or pull
request carrying a label matching `(?i)\b(bug|defect|regression)\b`, referenced as `#123` or `GH-123` in a commit
message; its report date is the issue/PR creation date. GitHub labels are often applied before triage (in
google/gson, some "bug"-labelled issues are support questions). Requiring a referencing fix commit in the
post-release window removes most of these, but labels from GitHub-tracked targets are noisier than Jira's, and the
manual-validation sample matters more.

Jira access: anonymous REST (Hibernate Cloud `/rest/api/3/search/jql`, batched 50 keys/request). Responses are
cached in `data/new/<id>/raw/jira_issues.json` and the run date is the cache's mtime (2026-10-24).

## 3. Validation of the EH-metric pipeline (Hibernate 5.0.0.Final)

`python src/collect/validate_against_original.py` reruns our JTratch + aggregation on the paper's own release and
compares all 107 file-level EH metrics with the authors' released values
(`results/pipeline_validation_hibernate-5.0.{csv,md}`). Files matched: 459 Catch_Based, 398 Try_Based,
823 Throws_Based.

* **57/107 metrics are identical on ≥ 95% of files.** Catch-level metrics: mean exact-match 0.96 (`# Catch`,
  Catch SLOC, Dummy Handler, Ignoring InterruptedException, Multi-line log, getCause, Throw within finally,
  Generic Catch, Nested try: all ≥ 0.99). Throws metrics: 0.99.
* Where the rule sheet left a choice open (Destructive Wrapping, Log and Throw, Overcatch, recoverability classes,
  generic types, nested try, LOC offset), we picked the variant that matched the released values best; the
  alternatives and their match rates are recorded in REPRODUCTION.md §9.
* **Possible-exception (flow) metrics match less well** (Try_Based mean exact-match 0.84; `# Possible Exceptions`
  0.48 exact, ρ = 0.84). Root cause: JTratch finds ~25% fewer possible exceptions per try (2.38 vs. 3.19)
  because (i) the authors' external-Javadoc XML (`/Users/gbp/javadoc/javadoc.xml`) is unpublished, so
  `% External Doc` is 0 for us vs. 0.36 in theirs; (ii) dependency jars were not on JTratch's classpath (the
  authors pointed it at their whole local Maven repo).

## 4. Data-quality issues and limitations

| Issue | Affects | Handling |
|---|---|---|
| Released dataset has no raw (catch/try-level) data; Tableau workbook unpublished | Phase 1 aggregation | Re-implemented from the rule sheet; validated (§3) |
| External-Javadoc XML unpublished | New-context flow metrics | Documented; regenerating it from JDK 8 + dependency `@throws` tags is a TODO |
| No dependency jars for JTratch | Flow metrics; more files lose all possible exceptions (467 → 404 for 5.1) | Documented; TODO: resolve Gradle/Maven deps and pass `--m2` |
| No Understand license | New-context BASE models | Fallback metrics; Phase 2 BASE/BSFC/BSAP on new data are an **extension**, not a faithful BASE |
| Pre-release window is a git range, not the authors' "release-notes" window | Process metrics of new contexts | Documented approximation |
| Release date = commit date of the tagged commit | Post-release cut-off | Hours-level differences only |
| Commit-message key linking misses fixes without a key, and may include partial or misc changes | Outcome label | 40-link manual-validation sample (to do) |
| JTratch is not run-to-run deterministic (6 flow metrics vary; catch/anti-pattern metrics stable) | Flow metrics of new contexts; BSFC | One analyzer run kept per release commit (reused); see REPRODUCTION.md §8 F1, T10 |
| ZooKeeper's previous release `release-3.5.0` (2014) is the first tag of the 3.5 line, so the pre-release window spans ~5.5 years and every file changed in it | ZooKeeper process metrics | Documented; a narrower window (e.g. the last 3.5.x patch) is an alternative to test |
| Umbraco 7.x issue tracker (YouTrack, U4-xxxx) is decommissioned | C# new context | Defect mining expected blocked; documented in targets.json |
| `-1` "not applicable" sentinel mixed with real zeros | All models (authors' choice) | Kept for faithfulness; the ML code clips to 0 before log-transforming for LR only |
